# Internacionalización y códigos de error

Cómo se nombran los códigos que devuelve la API y cómo se traducen a mensajes para el usuario. Forma parte de los [estándares del proyecto](README.md); el catálogo de códigos de este sistema está en [design.md](../design.md).

## Principio

El backend **nunca** devuelve mensajes destinados al usuario final. Devuelve un `code`, y el frontend lo traduce usando un diccionario.

| Campo | Audiencia | Puede cambiar |
| :--- | :--- | :--- |
| `code` | La máquina. Clave del diccionario | No. Cambiarlo rompe clientes |
| `message` | El desarrollador, en logs y depuración | Sí. Nadie depende de su texto |

La razón práctica: si el texto que ve el usuario vive en el backend, cambiar de idioma o mejorar una frase obliga a desplegar el servidor. Separándolos, el frontend lo resuelve solo.

## Convención de nombres

Formato `recurso_condicion` o `recurso_evento`, en snake_case y en inglés.

```bash
Correcto                        Incorrecto
place_not_found                 not_found
specialty_not_supported         unsupported_specialty
place_import_created            created
rate_limit_exceeded             error
```

Dos errores frecuentes:

- **Claves genéricas sin contexto.** `not_found` no dice qué no se encontró. El frontend no puede escribir un mensaje útil con eso.
- **Orden invertido.** `unsupported_specialty` nombra primero la condición. Rompe el orden alfabético por recurso y hace que el catálogo deje de leerse agrupado.

## Diccionarios

Un archivo JSON por idioma, en el frontend:

```bash
src/i18n/
  es.json
  en.json
```

Ambos son obligatorios. Las claves corresponden exactamente al `code` que devuelve el backend.

```json
// es.json
{
  "place_list": "Directorio consultado correctamente",
  "ip_not_allowed": "No tienes acceso al servicio desde esta red. Contacta al administrador",
  "specialty_not_supported": "Esa especialidad no esta disponible en el directorio"
}
```

```json
// en.json
{
  "place_list": "Directory retrieved successfully",
  "ip_not_allowed": "You do not have access to this service from this network. Contact the administrator",
  "specialty_not_supported": "That specialty is not available in the directory"
}
```

Reglas de los valores:

- Es el texto final que ve una persona: sin tecnicismos, sin nombres de campos internos, sin códigos.
- Cuando se pueda, dice **qué hacer**, no solo qué falló. Compara "Origen no permitido" con "No tienes acceso desde esta red. Contacta al administrador".
- Sin variables interpoladas dentro del valor. Si hacen falta, se usa un marcador tipo `{{field}}` y se resuelve en el frontend.

## Resolución en el frontend

```typescript
export function t(code: string, locale = 'es'): string {
  const dict = dictionaries[locale] ?? dictionaries.en;
  return dict[code] ?? dictionaries.en[code] ?? code;
}
```

Orden: idioma activo, idioma de respaldo, clave cruda. Ver la clave cruda en pantalla significa que falta una traducción, y es intencional que se note.

## Agregar un código nuevo

En el mismo cambio, sin dejarlo para después:

1. Agregar el `code` en el backend.
2. Agregar la clave y su texto en `es.json`.
3. Agregar la clave y su texto en `en.json`.
4. Registrarlo en el catálogo de [design.md](../design.md).

Un código que existe en el backend pero no en los diccionarios llega al usuario como texto crudo en inglés técnico.

## Errores con detalle por campo

Cuando la respuesta trae `errors.details`, cada elemento lleva su propio `code` y se traduce por separado con el mismo diccionario:

```json
{
  "code": "validation_error",
  "errors": {
    "details": [
      { "field": "pageSize", "code": "page_size_out_of_range" }
    ]
  }
}
```

El frontend traduce el código general y el de cada detalle.
